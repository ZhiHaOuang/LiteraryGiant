# LG 的四种职责、专项分析与前缀缓存

2026-11-25。调研依据为 LiteraryGiant 当前工作树（父仓库基线 `7c78a391`）、本机 DSH 源码、固定版本的 billion-context 及下列一手文献。本文是设计建议。验证范围为代码调用关系和上游内核测试，尚无这套方案的文学盲评或实际账号缓存数据。

## 二、billion-context 真正值得借的机制

阅读版本为 `9c8307c804c2f08908bfabd9e3711e818d160b1c`。项目名里的 billion 指长会话累计处理的输入，可以包含缓存重读；单次请求仍受模型窗口限制。作者报告披露了单用户观测、部分节省量依赖建模等限制。不能据此外推中文长篇的命中率或创作质量。[上游报告及限制](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/paper/model-driven-incremental-hierarchical-compression-training-free-multi-generational-context-management-for-long-lived-coding-agents.md#L294)

| 追到的实现 | LG 可采用的设计 |
| --- | --- |
| 压缩按历史位置放置摘要，保护开头的首条用户消息；展示历史引用时可以固定首次计算的长度标记，避免后续重算改变已经发过的文本。[摘要位置](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/kernel/src/prune.ts#L496) · [引用快照](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/kernel/src/render-refs.ts#L159) | 优先稳定同一模型实际收到的消息前缀，包含角色说明、工具定义和已授权材料。编辑一章后应换版本；无关任务编号或动态计数尽量留在后部。 |
| `collectBlockContent` 在保留摘要及压缩状态的前提下读取原内容。默认展开一层，允许选择完整展开；回读内容可作为当前轮工具结果追加。[回读实现](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/kernel/src/decompress.ts#L158) | 长篇的伏笔表可先定位到章、段、版本，由检查员定点回读当前可见的原文。核对后只将引证与结论返给主 Agent。正式正文继续由书库保存。 |
| DSH 集成用 `isSeeded` 和父会话信息识别带历史的分叉。普通派生任务启动全新上下文，本机 DSH 实现也明确声明这一点。[上游分叉判断](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/src/agent/dsh-native.ts#L1515) · [本机 DSH 子任务](../dsh/packages/subagent/subagent-spawn-in-process/src/index.ts#L45) | 成员按书、版本、截止章及身份得到任务资料。相同权限的两个读者检查可复用相同材料；作者掌握的谜底不进读者视角的请求，包含任务措辞、旧摘要及回读结果。 |
| 完整 DSH 包还介入模型请求、宿主自动压缩、手动压缩和重试配置；LG 自己也装配了压缩与工具结果裁剪。[DSH 集成](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/src/agent/dsh-native.ts) · [配置变更](https://github.com/ranxianglei/billion-context/blob/9c8307c804c2f08908bfabd9e3711e818d160b1c/dsh.bundle.patch.yml#L21) · [LG 装配](../dsh-plugins/lg-agent-teams/presets/index.js#L14) | 当前只借鉴前缀稳定和按需回读。等主会话确有长历史压力，再在隔离环境测整体插件对历史恢复、模型请求和自定义预设的影响。 |

本轮在 LitIsLand 隔离副本对固定提交的 `state-prune.test.ts`、`decompress-report.test.ts`、`regression-promote-after-prune.test.ts` 运行原测试，50 项通过，0 失败、0 跳过。该结果只覆盖三组内核行为。[上游测试目录](https://github.com/ranxianglei/billion-context/tree/9c8307c804c2f08908bfabd9e3711e818d160b1c/kernel/tests)

## 三、厂商和文学研究如何约束这个方案

| 一手来源 | 结果与适用边界 |
| --- | --- |
| [DeepSeek 上下文缓存文档](https://api-docs.deepseek.com/guides/kv_cache/) | 命中依赖已持久化的完整前缀单元。官方例子中先发 `A+B` 再发 `A+C`，第二次仍可能未命中；识别并持久化共同部分后，第三次 `A+D` 才能复用 A。因此要分别测冷启动、连续复用和同时首发。 |
| [DeepSeek-V3.2 技术报告](https://arxiv.org/abs/2512.02556) | 稀疏注意力提高长上下文计算效率，属于模型层改进。应用侧仍要自己测传入哪些信息、是否泄露未来情节、实际复用了多少输入。 |
| [字节 Seed 等的 Context-Folding 研究](https://arxiv.org/abs/2510.11967) | 模型进入子任务，完成后把结果带回主轨迹、折叠工作历史。论文含专门训练，评测集中于长程研究和软件任务。LG 可独立试验「主 Agent 只收结论和可回读来源」，无需先移植训练方法。 |
| [火山方舟上下文缓存文档](https://docs.volcengine.com/docs/ark/context-cache?lang=zh) | 供应商还可以提供显式缓存或续接接口，调用条件依模型和协议而异。LG 的任务协议应传作品版本、可见材料和任务目标，底层供应商参数留在适配边界。 |
| [Re3 长故事生成研究](https://aclanthology.org/2022.emnlp-main.296/) | 计划、相关故事状态、重排与修订组成的系统在英文故事人工评审中提高了情节连贯性。这给 LG 选择「读者能否从前文理解回收」作为验收题提供依据。它没有单独测出一个分析员、某种缓存策略或中文笑点的收益。 |

## 四、四个职责怎样配合

| 职责 | 接到什么任务 | 返给谁、交付什么 |
| --- | --- | --- |
| 主 Agent `lg` | 与作者讨论，识别直接答复、专项检查、规划、创作的需要，选定材料与可见范围 | 给作者答复或供选择的建议；跟踪采用或暂缓。只在能改变当前决定时派发成员。 |
| 分析 `lg-analysis` | 带一个具体问题阅读指定版本；可用普通分析、伏笔核对、读者试读、语气检查等任务说明 | 给主 Agent 可定位的证据、观察、推断及未知；只做检查时允许无问题。 |
| 规划 `lg-planning` | 作者需要设计伏笔、安排回收、调整节奏时，取得获准使用的规划及必要证据 | 候选剧情或场景安排，说明埋设和回收的联系、可能代价，供作者选择。 |
| 创作 `lg-writing` | 按创作要求、已选方案及视角允许的资料写作，可在目标明确时直接受派 | 给作者候选正文。专项检查发现问题时，可只重写相应段落。 |

**分析的公共提示词建议保持三句。** 可先试用这段：「只阅读本任务提供、且在指定视角可见的材料。区分原文事实、人物相信的事、读者可推断的事和未知；有具体判断时给出章段与短引。材料不足就说明缺什么，检查后也可以建议保持原文。」现有调用与提交要求按真实运行路径附上。插件选择一个固定的专项说明，再附作者本次目标；专项选择与可用工具由宿主落实。首轮不需要新增公开角色、Skill 或可执行任意提示词的配置系统。

同一个伏笔可拆成两个问题。**知情核对**可看到已批准的回收意图，任务是「前文哪处细节能支撑将来的回收？若无依据或太直白，请定位」。**读者试读**只收到揭示前的正文，先问「读到这里，你还记住哪些未解释的细节？也可以没有」。将试读答案交给知情的主 Agent 比对。把谜底写进试读目标，会直接污染这次验证。**语气检查**只看近 2–3 章和作者的语气要求，区分人物声音、笑点落点及对场景节奏的影响；葬礼等场景的合格结论可以是保持沉默。

书级节奏偏好可选。作者启用「每 20–30 章复核伏笔」时，宿主为本次区间抽一次并保存到期章，重启或重跑沿用原值。分别记录上次实际埋设、上次检查及延后决定，防止重复提醒。到期只触发检查；「要不要埋」交回创作决策。短周期语气复核同理。两种观察彼此独立且都到期才有并行价值。

## 五、最小试验与采用门槛

1. **先离线看真实请求。** 两个检查使用同一版本的素材，各变更一个目标。在模型适配器出口用假供应商捕获有序消息及工具定义，找首处分叉；对照目前「编号、任务、工具回读正文」与「相同权限的公共说明、工具、已授权原文在前，变动目标在后」。正文继续作为用户数据传入。只在受限测试样本做捕获，记录长度、摘要值及字段位置。另在作者目标、资料、历史摘要和回读入口植入读者不可见的虚构谜底，逐项确认隔离。静态公共前缀不能当成实际命中量。
2. **再验证专项说明是否改善文学判断。** 两道校准题、至少两道冻结的新题，覆盖有效伏笔、无依据的疑似线索、适合轻松及应保持严肃的段落。对照现有公共分析与「稳定公共规则＋单项说明」，两组用同一模型、同一可见材料、同一输出要求。作者匿名评阅定位是否准确、是否多报问题、是否愿意采用建议，并记录用建议修订后正文是否更好。旧通用校验对空发现有限制，这项若统一放宽，两组须用同一检查专用契约，并单独记录谁选择保持原文。
3. **有用才测轻量执行。** A 用现有受限预设，先取资料再提交；B 在相同预设中预先提供同一份已授权材料，只留结果提交；C 复用 B 的输入与提交，只换轻量装配。A/B 检验省一次取资料往返的作用，B/C 检验预设本身。宿主应能证明哪份快照已交给该成员，并在提交时核对版本；保留已有来源校验。原生 Minimal 有软件工程人设、图片读取和持久 Shell，不能凭名称预判费用。另设主 Agent 直接完成同一检查的对照，判定独立成员是否值得。[原生 Minimal 配置](../dsh/packages/bundle/web-app/presets/minimal.patch.yml#L11)
4. **单独验证缓存和成本。** 保持同账号、模型、参数、工具权限和材料一致，只交换固定与变动内容的位置。分冷启动、相同资料的串行第二及第三次、并发首发记录。看供应商回传的读取命中输入、总输入、生成输出、往返次数、端到端耗时，以及每条作者认可反馈的总成本（包括主 Agent、工具后续轮与失败）。把有用量回执的请求占比一并列出；缺失回执记未知、无可核算账单就报告 token 和次数。无需为制造命中给每个成员塞整本书。[LG 现有请求计量](../dsh-plugins/lg-agent-teams/src/telemetry.js#L51)

**采用顺序。** 先证明专项检查能在新题中给出可用反馈，而且没有越界信息、伪造引文或强制制造问题。随后才以成本和延迟挑执行方式。同等可用性下如果主 Agent 直接做更省，就保留直接路径；只有轻量装配相对预供材料的现有预设仍有可复现收益，才值得维护它。若长会话实测出现摘要丢线索，再单独测试可回读的压缩。第一轮建议只取「伏笔读者试读」做离线请求与可见性验证，不触及日常 Beta 配置。
