## 研究来源与采用方式

附件报告已完整阅读；其中以 Codex 为宿主的旧建议由作者本次 DSH 决定替代。只吸收适用机制，不嵌入另一套自主 Agent 框架。

- [Oh Story tracking_commit.py](https://github.com/zenstory-ai/oh-story-claudecode/blob/main/skills/story-import/scripts/tracking_commit.py)：读取原始实现，参考版本前置检查、按项目串行提交和派生视图边界。实现以 LG 的 SQLite/来源协议为准。
- [ainovel-cli](https://github.com/voocel/ainovel-cli)：读取原始 README，参考确定性路由、步骤检查点、滚动规划和逐章审阅。其自动提交默认不作为 LG 默认。
- [DOME，NAACL 2025](https://aclanthology.org/2025.naacl-long.63/)：动态层级大纲和记忆协作，拟用于 lg-planning；不强制引入图数据库。
- [ConStory](https://arxiv.org/abs/2603.05890)：有原文证据的一致性判断，拟用于 lg-review。检测结果仍可误报，不代表自动证明全书一致。
- [MUSE](https://arxiv.org/abs/2609.15188)：研究设计、人物表演、场景构成与修订的中间成果。先按公开论文研究机制，未复制其非商业许可技能/语料，不把理论名称当质量证据。
- [BookWorld，ACL 2025](https://aclanthology.org/2025.acl-long.773/)：人物与世界互动用于创意排练，产物保持候选，不自动进入正文。

其他附件来源继续按具体需求核实，明确采用/不采用理由；研究报告不是要求将所有项目都搬入仓库。

## 验证阶梯

1. LitIsLand 隔离代码与合成作品，先做领域回归，再加载真实 DSH Host。
2. 复制经过验证的最小文件集到项目，运行实际插件入口与 UI；验证停用/卸载生命周期、打包文件、重启恢复。
3. 真实模型任务使用同模型、同要求、同材料比较；记录完成率、范围保持、证据、调用数、token、等待和费用。先检验实用结果，再谈效率收益。
4. 完成逐项迁移后执行依赖审计：新插件可在没有 LiteraryAgent Python 环境、Codex 二进制和旧 app_server 的安装中完成核心文学闭环。
5. 最终逐项审计上表和用户五项要求；测试、UI、真实调用证据必须覆盖同一范围。全部证明前目标保持 active。

### 故事规划迁移补充

`lg-planning` 已迁入创作方向、场景设计与层级骨架：

- 兼容 `lg.creative-decision.v1`，三个不同候选；作者选择精确历史版本，新增选项保留旧选择，撤回不会回退。来源允许当前草稿作为计划依据，不自动提升世界事实。
- 场景卡支持创建、设计编辑、归章/排序、字数范围与标签保留。模型新计划保存在 `metadata.lg_plan_proposal`，不覆盖已批准计划；作者批准核对场景卡及正文版本。设计/归属变化要求重新批准，旧正文保持。
- 作者可创建和调整卷/章骨架；同卷近期 1–10 章窗口（默认 3）拒绝歧义顺序，不自动生成远期细纲。此处借鉴 DOME/ainovel-cli 的层级和近期细化边界，不声称复现论文效果或实现完整自动规划器。

## 单条整章流程中的构思、作者选择与改稿

在整章创作中启用「先生成三个方向，再由我选择」，保存构思要求、目标章、起草要求、审阅要求与总预算。首步复用 plot 专家和规划插件的三个备选。流程存下原版本与选项，作者在此预览一个方向后单独确认；规划选择与流程收据在同一数据库事务提交。对同一收据重放保留原结果，关闭流程会使未提交的确认失效。故事规划里的作者选择也会在工作流读取时重新核对。每次起草都要求当前选择对应本流程的原方案版本。

独立桌面使用本地适配器验证完整流程：保存时零调用，生成三个方向后停下。重启后作者预览第一条的起草输入，另一作者操作改选第二条，旧预览被拒绝且没有增加调用。按第二条起草后，审阅、勾选问题并改稿，两版均留作候选，编辑台最后采用修订版。合计四次本地调用，正式模型账本没有新增费用。模拟规划已写入而工作流尚未登记完成的中断，也验证了重启恢复原三项结果。通用跨章流程和旧 RunStore 导入仍待迁移。

## 旧 RunStore 公开历史导入

lg-books 从当前登记作品的 .literarygiant/runs 分页列出 v2 清单。按单条运行核对目录、事件归属、lg.literary-task.v1 状态指纹、已完成步骤和本书实际保存的正文版本。事件文件逐块读取，只保存公开事件字段；失败诊断使用公共摘要。每条事件上限 4 MiB，公开快照总量上限 4 MB。原机器记录的绝对路径不用于读取外部文件。

lg-workflows 的旧版运行历史按公开内容摘要预览、确认并保存快照。同一内容的重试复用原快照，公开记录变化时要重新预览。打开关联版本前重新核对文档、版本号、来源运行与正文摘要。导入保留当时的状态，旧生成操作的恢复、来源收据迁移和旧产物采用仍待迁移。

使用原 Python RunStore 和文学任务写入端、合成适配器生成一部测试书，包含三个方案、作者选择及候选版本。桌面预览后更改清单，旧确认被拒绝；重新导入和重复提交共生成一份快照。将合成源运行目录移出后冷启动，在旧记录中查到三个选项，编辑台打开原候选，正式正文版本未变。两套回归均通过 311 项，17 个独立归档共 204 个成员与安装位置及项目源码核对，23 个插件条目均在桌面运行。没有新增付费调用。

## 逐章起草与已采用章末衔接

lg-workflows 接收 2–6 个章节和每章的任务要求，逐章核对版本、材料、模型及预算。每步保存候选，作者采用、采用修订版或拒绝后才能推进。开启衔接时，lg-context 从最近已采用章读取结尾，按 UTF-8 字节预算留取末段，在收据中保存完整正文摘要及版本。前章来源变更时，基于旧输入的后章候选无法直接采用。未完成工作流收据的已保存起草可以从原账本恢复。

本地适配器和独立桌面验证了冷启动后采用、超长前章只取末段、拒绝后章、结束后重放零新增调用。真实 GLM-4.5-Air 的前章 131 个汉字，包含指定结尾「她把蓝纽扣藏进空火柴盒，压在灯座下。」；为继续实验在合成作品中采用了前章。后章要求未重复物件和地点，生成 121 个汉字，学徒从灯座下的火柴盒发现蓝纽扣。前章人称在“他”和“她”之间变化，后章增加了无前文依据的海难赠物背景，未明确纽扣最终是否放回盒内。后章仍是候选。两次调用用量估算合计 ¥0.0052752。
